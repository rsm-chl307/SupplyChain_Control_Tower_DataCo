## Architecture and trust boundary

`EightCallCampaign` uses a **separate, explicitly provisioned local SQLite file**. Its only provisioner is `provision_offline`; the persisted mode is constrained to `OFFLINE_TEST`. There is no paid mode, no `execute` method, no SDK client and no provider call. The proposed $0.02 per-call / $0.16 aggregate values were **not configured**. Tests use an isolated $0.01/$0.08 **offline test policy**, which grants no executable paid allowance. A future paid gate requires separate design, authorization and tests.

The immutable canonical campaign plan fixes exactly `EV-01` through `EV-07` and `EV-08-LR`, case versions, fixture IDs, scenario/selection, candidate model ID, offline model policy and test snapshot, current P2 request limits, pricing-basis label and explicit offline test ceilings. The manifest SHA-256 is persisted; each slot template is checked against it on open and before writes. `EV-08-LR` must use the separately admitted trusted Low-risk fixture. The seven other slots require the original trusted fixture.

The service opens the store through the existing P3 `ApprovalStore` file/identity checks and compares its persisted Owner verifier to `OwnerVerifier.from_environment()`. An explicit Owner password is required for provisioning, each slot approval, revocation and reconciliation. Demo login and caller-supplied verifier objects are never accepted as authorization. The local trusted-process limitation remains: a compromised local process or privileged file administrator is outside the assurance boundary.

`_binding` calls `ValidatedBrief.verify()`, rebuilds the request with the existing `build_request`, runs `verify_request`, checks the validator-issued selection against the immutable slot, and hashes campaign/slot identity, Brief digest, minimized projection digest, Request Digest, model/policy identity, schema/instruction/privacy versions and limits. Approval records contain the resulting binding digest, Request Digest, time, expiry, revocation, one-use consumption and offline estimate/ceiling. EV-01 and EV-07 can have identical Request Digests; their `(campaign_id, case_id)` and independently consumed approval references remain distinct. No Streamlit session value is authoritative.

## SQLite transaction and state design

The new store has one campaign row, exactly eight slot rows, slot approvals, per-slot reservations and append-only events. Foreign keys are enabled. Event UPDATE/DELETE triggers reject ordinary modifications. `ApprovalStore` requires the database and identity marker to be regular, permission-restricted, matching files and opens existing SQLite in `mode=rw`; missing, replaced or corrupt storage fails closed. `quick_check`, manifest/roster checks and the aggregate reservation invariant run on open and before state-changing transactions. These controls are not tamper-proof against an administrator who can alter code and both files.

Reservation uses `BEGIN IMMEDIATE`. It rechecks the live Brief/request and exact unexpired, unrevoked, unconsumed approval; conditionally increments the aggregate by the **full per-slot ceiling**; inserts one immutable reservation; consumes that slot's approval; and appends digest-verification/reservation events in the same transaction. A failed check rolls back all writes. Uniqueness constraints and SQLite's writer lock prevent duplicate local-process reservations. The reserved aggregate never decreases after success, failure or UNKNOWN. Estimated cost, reserved ceiling and observed charge are separate integer micro-USD fields; a durable summary exposes each and counts missing charges.

Unreserved slots display `NOT_STARTED` without a reservation. A reserved slot begins `NOT_STARTED` and is already consumed. `start_offline_attempt` changes it once to `IN_PROGRESS` with a unique attempt ID; it records a **synthetic test-double event only** and never submits a request. Only an attempted slot can become `SUCCEEDED`, `FAILED` or `UNKNOWN`. A definitive outcome requires explicit sanitized usage and charge evidence, including explicit zeroes when applicable. Missing accounting cannot become definitive success/failure. UNKNOWN retains its reservation and holds the campaign. An unresolved `IN_PROGRESS` blocks new reservations after reopening; it cannot reset automatically. A reserved-but-undispatched slot cannot be released or rebound. Owner-attested `reconcile` moves reserved/uncertain work to UNKNOWN and keeps the campaign held, with no retry or allowance restoration.

Append-only events cover provisioning, approvals/revocation, digest verification, reservation, offline attempt, outcomes, usage/charge observation and manual reconciliation. Provider accounting is limited to token counts, a bounded request ID, exact nonnegative charge and sanitized note. No API keys, credentials, full Briefs or request/response bodies are logged. A reported over-ceiling charge is retained as evidence and holds the campaign; a local ceiling cannot cap provider billing. No actual usage or charge was observed in this task.
