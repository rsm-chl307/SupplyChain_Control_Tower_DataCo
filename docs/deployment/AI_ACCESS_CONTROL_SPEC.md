# Stage 2 — AI Access Password contract

> **Stage 5 update, 2026-11-26:** `cloud_access.py` now issues a process-signed 30-minute grant after successful scrypt verification. `CloudAIService.ask()` verifies it again in the backend before every Fake provider call; changing a session expiry flag does not grant access. The existing five-failure session lockout remains. Per-grant and process-local request limits are implemented, but cross-session, cross-worker and restart-persistent abuse protection is not. The real provider remains locked. See [Stage 5 security review](STAGE_5_SECURITY_REVIEW.md).

> **Stage 4 implementation update, 2026-11-25:** The existing Streamlit Decision Copilot now invokes `check_ai_access_attempt()` through a masked form submit callback. The callback deletes the password widget state before rendering and stores only a 30-minute access expiry, failure count and lockout timestamp. Five failures lock that browser session for 15 minutes. Public Planning remains accessible; no AI Context/Provider button is rendered before authentication. Synthetic AppTest verifies the test password is absent from session-state representation after submit. The existing local Owner Approval is a separate historical workflow, not the Cloud AI gate. Real provider dispatch remains locked; session-only throttling is not a durable Stage 5 quota.

Date: 2026-11-25 UTC. Stage 2 prepared the backend gate; the Stage 4 update above records UI integration. Neither stage grants paid dispatch or wires the UI to OpenAI.

`src/ai_copilot/cloud_access.py` accepts an entered password and Secret-held salt/verifier. It derives scrypt (`n=2^14, r=8, p=1`, 32-byte output) and compares with `hmac.compare_digest`. Missing/malformed configuration fails closed with no secret details. A helper records only failed-attempt count and lockout timestamp in a caller-supplied session map: five failed attempts lock that browser session for 15 minutes. The password itself is never stored in that map. Offline tests use a synthetic password and salt.

The Stage 4 UI now invokes this gate for Fake AI preview through a masked input and removes plaintext from `st.session_state` on submit. Future paid use must check access before obtaining API credentials or issuing a request, and must enforce request/token/cost controls independent of the password. A new browser session can evade session-only throttling; this helper is a basic UX protection, **not** a cross-session anti-abuse guarantee. The Owner has approved one app with AI Password, not a separate AI product.

Future qualification must test anonymous rejection, correct/incorrect passwords, missing config, session expiry, reruns, leaked frontend state, concurrent attempts, logging redaction and restart behavior. No actual Owner password was requested or configured in this stage.
